## [Unreleased]

### Fixed
- **Hydration mismatch on the collapsible sidebar / workflow list.** `Sidebar` and `FlowWorkspace` read their persisted collapse preference in the `useState` initializer, so the server rendered *expanded* while the client's first render was *collapsed* ("IGRIS AGENT…" vs "IA") — React flagged a hydration error. Built-in agents are left **unassigned** rather than guessed; `parentId` continues to carry reporting (no duplicate `reportsTo` column yet). **No execution/delegation; F0.2 Mission/Task, F1 Manager, F2 Agent Factory, and G-Brain F3 are NOT started.** See `docs/ARCHITECTURE.md` §6b.

- **Human Approval node + durable pause/resume** (Phase E): a workflow can now include a **Human Approval** node — a human gate kept strictly separate from the machine-logic Decision node. When a run reaches one it opens a `pending` approval and **pauses durably** (run status `waiting_approval`), surviving browser refresh, navigation, Next hot-reload, and full process restart (the reconciler leaves waiting runs alone; only `running` runs go `interrupted`). `resumeWorkflowRun(runId)` reloads the **immutable** version, rebuilds scheduler state from the persisted node runs, applies the human decision, and continues **without re-running any succeeded node** (no upstream LLM/tool re-calls — proven by an executor call-count test). Approval routes exactly like a Decision: approve activates only the approve-route edge, reject only the reject-route edge (a rejection is a normal outcome down the reject branch, **not** a `failed` run; the node gets a distinct `rejected` status). Resolution is **idempotent** — a conditional `UPDATE … WHERE status='pending'` means approving twice resolves once and resumes once; the process-wide active set is the resume lock. New APIs: `GET /api/flow-approvals` (inbox), `GET /api/flow-approvals/:id`, `POST /api/flow-approvals/:id/approve|reject` (Zod; the client sends only id + decision + optional note — the run/workflow/routes come from the persisted row, never the client). ### Fixed
- **Hermes ACP timeout no longer poisons the persistent process.** On a per-prompt timeout the client now sends `session/cancel` and cleans up the leaked request correlation (and always clears the timer), so the shared `hermes acp` process is freed and the next request can succeed. Setup requests (`initialize`/`session/new`) are now timeout-bounded, and safe diagnostics were added (request/session id, elapsed, timeout, process-alive — never prompts/keys). New env: `HERMES_ACP_ARGS`, `HERMES_ACP_DEBUG`. Timeout failures still surface as `hermes_unavailable` with no silent model fallback. (See `docs/INCIDENTS.md` INC-005.)
- Flow runs were falsely marked `interrupted` while still running — the in-process active-run registry was not shared across Next.js per-route bundles. Pinned it to `globalThis`. (See `docs/INCIDENTS.md` INC-001.)
- Canvas node "Delete" previously deleted the underlying agent everywhere; split into non-destructive **Remove from canvas** vs a clearly-labeled two-step **Delete agent**. (INC-004)
- Provider connection status no longer shows a false "connected" from mere key presence; a real backend check is required (`unverified`/`connected` states). (INC-003)

### Security
- **Approval endpoints are backend-authoritative:** the client sends only the approval id, the decision, and an optional note — the run id, workflow, node, and routes are read from the persisted row, so a client can never make one approval resolve a different run. Approval `context_json` holds non-secret workflow data only (never credentials/tokens); the `secret.request` value is never displayed. Human Approval nodes and Hermes `approval/sudo/secret.request` events are **never auto-approved** — only a human resolves them.
- Provider API keys live only in `.env.local`; the DB stores presence/status, never the value; frontend receives `hasCredential` only.
- Provider/adapter errors are redacted before persistence/surfacing.
- Blank credential on update does not erase or reveal a stored key.

### Known Issues
- **HRA-2:** `hermes serve` is now a **selectable** production transport (H3) but **ACP remains the default**; serve is not the default for anyone. Conditions before serve could become a default: **MCP-specific execution over serve not isolated** (server-side tools incl. real email DID run) → MCP partial; **skills parity unverified**; **persistent-memory isolation** via a dedicated Hermes profile is a pending product decision (Hermes memory persists across sessions, independent of IGRIS G-Brain). Remote Hermes (H4) not implemented.
- Workflow execution is sequential (Parallel branches run in a deterministic order, not truly concurrent — correctness over literal simultaneity). Memory (Phase F) nodes remain placed-but-rejected-before-run; Approval nodes are now runnable (Phase E). Approvals have no expiry/TTL yet (`expired` status is defined but never produced) and no auth layer (resolver actor is `local_operator`).
- Static reference validation checks only the reference ROOT (that the source node exists); deeper runtime paths cannot be proven at publish time.
- `auto` model strategy is a stub (fails `auto_not_implemented`); no fallback/retries/cancel.
- Hermes ACP reports no token usage → node token counts `null`; estimated cost `null` (no fabricated pricing).
- Stale-run detection is on read (→ `interrupted`); no background sweeper or auto-resume.
- Two seed/api render tests are intermittently flaky under full-suite parallel load (pass in isolation / on re-run).
