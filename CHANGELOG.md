## [Unreleased]

### Added
- **`research.web` is now a REAL, tool-backed capability — live web search (Tavily, search-only).** The prior fix correctly made eligibility tool-backed, but no web/search connector existed, so `research.web` was permanently a tool gap. Inspection confirmed NO existing web/search implementation and NO search credential configured anywhere, so a provider + credential decision was surfaced to the operator (chosen: **Tavily**, **search-only**). A new connector `lib/connectors/websearch.ts` performs genuine public-web search and is registered as the canonical `web.search` tool (now in `WIRED_TOOL_SLUGS` and the Factory allow-list); the `research.web` requirement points at it. An agent that carries `web.search` (with `TAVILY_API_KEY` set) can retrieve current public info and cite sources; without the tool — or the key — `research.web` stays an honest, explicit tool gap. **Search-only by design** (no arbitrary URL fetch → no SSRF surface); **honest failure** (no key ⇒ setup guidance + no network call; provider/timeout errors surfaced, never fabricated results, never a silent model-only fallback). No fake results, no loosened safety rules, no auto-granted tool, no invented credential; the resolver/dispatch-preflight/eligible-agents API were already generic so the new tool flows through unchanged. No DB change; existing agents are not mutated. 9 new connector tests + reframed/positive eligibility tests; **1649 tests green** + tsc clean. Verified live on 4100: Web Search shows `not_configured` (never fake-connected); the real "Collect Daily AI Updates" task reports the honest tool gap, and a `web.search`-equipped agent flips to eligible (then cleaned up, no residue).

### Fixed
- **Capability ≠ Tool — a capability label no longer implies real tool access.** Manual E2E found a false-eligibility bug: a task needing `research.web` detected a gap, the Factory proposed + a human approved an agent labelled `research.web`, the Manager dispatched it, and the task FAILED — because the approved agent had no actual live-web/search tool (it relied on Slack/shared notes). Eligibility for a **tool-backed** capability now requires BOTH the capability AND that a required, WIRED tool is genuinely available to the agent (never inferred from instructions). A small, generic `capability-tools` registry maps only the capabilities that need a tool (`research.web` → one of `web.search`/`browser.search`/`web.fetch`; none is wired, so it stays an explicit **tool gap**); model-only capabilities (analysis, summarization, `research.market`) are unchanged. `resolveAgentsForCapabilities` enforces this by default; the Agent Factory refuses to propose/promote an agent for a tool-backed capability it cannot tool-back (fail-safe, no agent, clear reason — no invented connector, no auto-grant); dispatch runs a **preflight** so an assigned-but-tool-deficient agent is never started (task stays queued with an explicit `tool_gap`, no `AGENT_STARTED`, no wasted LLM run). The eligible-agents API + `/missions` now explain the missing tool. No DB change; existing agents are not mutated. 14 new tests; **1636 tests green** + tsc clean; verified live on the real "Collect Daily AI Updates" task.
- **Operators can now read an agent's actual result — "View Result" on `/missions`.** A Company Artifact showed on the Mission page as plain, non-clickable text with only a "Promote to G-Brain" action, so the operator could not read the work the agent produced. The artifact row's title is now clickable and a **View result** action opens a focused detail modal showing the title, type, full **result** (strings rendered readably, structured JSON pretty-printed — never `[object Object]`), summary, and provenance (Mission · Task · producing agent/workflow · created time), plus **Promote to G-Brain** and **Close**. Full content is fetched ONLY by the explicit per-artifact detail read (`GET /api/company-artifacts/:id`, which already existed and is reused) — broad mission/report feeds keep the content-free safe projection. Viewing an artifact NEVER promotes it (the read is a `GET`); Promote stays explicit + idempotent. No DB change, no execution/Manager/creation change. 8 new tests; **1622 tests green** + tsc clean; verified live on the real "Define Top AI Scope — result" artifact.

### Fixed
- **Hydration mismatch on the collapsible sidebar / workflow list.** `Sidebar` and `FlowWorkspace` read their persisted collapse preference in the `useState` initializer, so the server rendered *expanded* while the client's first render was *collapsed* ("IGRIS AGENT…" vs "IA") — React flagged a hydration error. Both now start expanded (matching the server) and hydrate the real preference in a mount `useEffect`; the pre-paint `--nav-w` init script keeps the width correct, so there is no flash. No behavior change.

- **Agent Factory** (Architecture V2 · F2 — the fourth V2 checkpoint; closes the F1 capability-gap loop): CONTROLLED, HUMAN-GATED dynamic agent creation. When no existing agent (and no published workflow) can satisfy a Company Task, the operator can **Propose an agent** to fill the gap — an LLM proposes a spec, but the **SERVER owns safety** (validates against a `FactoryPolicy`: connector-backed tool allow-list bounded in count, allow-listed model, bounded instructions, `maxDepth`, `canSpawn=false`; a violating spec **fails safe** and creates nothing). **Proposal-first / create-on-approve:** the pending artifact is a `company_agent_proposals` row; **`createCustomAgent` runs ONLY on human approval** (promotion) — so no agent is ever created silently, and there are no disabled orphan agents. Promotion reuses the **Phase-E idempotent-resolve PATTERN** (conditional `WHERE status='pending'` — a double-approve promotes once), not the `flow_approvals` table (there is no run to resume) and **no second approval authority**. On approval the server upserts the gap capability defs → creates the agent under the stored policy → assigns **EXACTLY the task's gap capabilities** (never the LLM's list) → the **F1 resolver now matches**, so the next Manager Step dispatches the task. Factory agents are **temporary + mission-bound**: `retireTemporaryAgents` (called from `managerStep` on mission completion) disables the agent + removes its capabilities — **reversible, not deleted**. **Operator-triggered only — no auto-propose, no autonomous loop.** New Zod APIs (no generic executor): `POST /api/company-tasks/:id/propose-agent`, `POST /api/agent-proposals/:id/approve`, `POST /api/agent-proposals/:id/reject`, `GET /api/missions/:id/proposals`. `/missions` gains a per-gap **Propose agent** button + a **Proposals** review strip (Approve/Reject). Additive `company_agent_proposals` table (+2 indexes); `custom_agents`/`CustomAgent` schema unchanged (factory metadata lives on the proposal row). **Budget** is stored + surfaced as a constraint but **not** hard-metered at runtime (agent_runs `cost_usd` is the honest seam). **Department managers, semantic matching, and G-Brain F3 are NOT started.** See `docs/ARCHITECTURE.md` §6e.
- **Executive Manager / Delegation Engine** (Architecture V2 · F1 — the third V2 checkpoint; IGRIS becomes a real AI-company operating system): the **Executive Manager** plans a Mission, decomposes it into Company Tasks, capability-matches (F0.1), and DELEGATES to an existing agent OR an existing published workflow — recording structured Artifacts, an append-only event ledger, and a report. It **evolves the existing Conductor** (tagged `role: 'executive_manager'` in the runtime registry — no duplicate id; still the chat/ASK operator brain) and reuses the existing agent runtime + Workflow Engine + Phase-E approvals + F0.1/F0.2 foundations. **Three roles stay separate:** Commander = owner surface · Executive Manager = AI manager agent · Workflow Engine = deterministic SOP executor. **Planning ≠ execution:** the LLM proposes a plan but the server owns safety (Zod-validated; **server-generated task ids**; F0.1 capability + F0.2 dependency validation; bad plan fails safely; apply is idempotent by title). **Deterministic delegation policy:** valid published workflow → workflow; else an eligible assigned/selected agent → agent; else **CAPABILITY_GAP** (task stays queued, structured gap reported — **F1 NEVER creates an agent; that is F2**). Agent selection is F0.1 rank PRIMARY, real U5 presence only refining (prefer non-busy; never fabricated). **Dispatch reuses existing infra** — agent path → `createRuntime(...).run(id)` (one `agent_runs` row); workflow path → `startRun` on the **immutable published version only**, synced by `reconcileTask`. **Idempotent** (a running/terminal task is never re-dispatched; one artifact per execution) and **durable** (task state + a new `executionKind`/`executionRefId` on `company_tasks` survive restart — never overloading the workflow `runId` with an agent-run id). **First-class Artifact** (`company_artifacts`, traceable to mission/task/execution, SAFE projection for feeds — **no G-Brain ingestion**, no auto durable memory). **Append-only event ledger** (`company_events`, emitted only after canonical state persists, best-effort, bounded/safe metadata — NOT canonical state). **Bounded `managerStep`** (reconcile → promote satisfied deps → dispatch ≤ maxSteps=3 → deterministic completion; **no autonomous/infinite loop**). **Human Approval reuses Phase E** — a paused workflow moves the task to `waiting_approval` + `APPROVAL_REQUIRED`; **no `company_approvals`, no second approval authority**. New Zod APIs (no generic execute-anything): `POST /api/missions/:id/plan`, `POST /api/missions/:id/manager-step`, `POST /api/company-tasks/:id/dispatch`, `GET /api/missions/:id/report[?synthesize]`, `GET /api/missions/:id/events`, `GET /api/company-artifacts/:id`. `/missions` gains Plan / Manager Step / per-task Dispatch + a deterministic report strip + the event list. Additive tables `company_artifacts` + `company_events` (+ indexes) and 2 additive `company_tasks` columns (idempotent migration). **F2 Agent Factory, department-manager hierarchy, and G-Brain F3 are NOT started; no parallel workflow engine, no second approval system, no autonomous loop.** See `docs/ARCHITECTURE.md` §6d.

### Security
- **Approval endpoints are backend-authoritative:** the client sends only the approval id, the decision, and an optional note — the run id, workflow, node, and routes are read from the persisted row, so a client can never make one approval resolve a different run. Approval `context_json` holds non-secret workflow data only (never credentials/tokens); the `secret.request` value is never displayed. Human Approval nodes and Hermes `approval/sudo/secret.request` events are **never auto-approved** — only a human resolves them.
- Provider API keys live only in `.env.local`; the DB stores presence/status, never the value; frontend receives `hasCredential` only.
- Provider/adapter errors are redacted before persistence/surfacing.
- Blank credential on update does not erase or reveal a stored key.
